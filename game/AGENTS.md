# 游戏关卡实现约束

## 核心原则：因果必须可见

玩家不应该只从工作台文字或结果颜色猜出解法。凡是“触碰 / 观察 / 等待 / 记录 / 接线”等动作会改变世界，都必须同时满足：

1. 关卡画面中有可辨认的实体来源（例如拉杆、地板、符文、胶囊、传感器和手臂），并且它所在的位置与程序动作的目标一致。
2. 触发后要有明确的中间反馈和最终状态。门、地板、站点、线路、摆臂等不能从旧状态瞬间跳到新状态而没有过程。
3. 失败也要留下可定位的物理证据：哪个对象被触发、哪个目标收到动作、在哪个节拍失败，都应能从画面或消息追踪。
4. 工作台中的配置必须反映到世界画面。尤其是接线、携带物、记录内容等玩家可编辑状态，不能只在模拟器内部生效。

## 确定性与表现层

- `sim.ts` 只描述离散 tick 的纯状态转移；不能读取 DOM、Pixi、`Date.now()` 或随机数。
- 需要动画时，在状态中记录触发 tick / 当前动作，再由 `view.ts` 计算确定性的进度；不要把 wall-clock 时间塞进模拟逻辑。
- `game-shell.ts` 的绘制函数必须消费 view 数据，不要复制一份与模拟状态可能漂移的隐藏状态。
- 新增动作时，同时补齐：可见实体、动作中的反馈、成功/失败反馈、英文和中文文案，以及模拟测试。

## 关卡导航与可读性

- 游戏页必须提供可见的自由选关入口；当前关要高亮，上一关 / 下一关在边界处明确禁用。
- 选关和通关后的进入下一关必须复用同一套 `loadLevel` 流程，切换时重置运行状态、编辑器和画面，避免出现“按钮变了但世界仍停留在上一关”的错觉。

## 按步调试

- 单步调试第一次点击要从当前编辑器内容创建新的运行历史并推进一拍；之后每次点击只能推进一个 tick。
- 自动运行和单步调试必须使用互斥状态：自动运行时单步按钮不可用，调试状态下自动运行不可用，但可以重置后重新开始。
- 单步推进必须由 tick 驱动提供同步 `step()`，不能通过缩短计时器或依赖墙上时间实现；成功 / 失败后立即停止并保留最后一拍的画面与消息。

## 场景边界

- 所有 Pixi 实体都必须落在 `900 × 440` 的世界画布内；移动门、墙、碎片等固定尺寸实体不能只移动位置而忽略自身高度。
- 门墙这类“移出开口”的动画要在 view 层计算可见区域或裁切高度，最终状态必须不可见或停在开口边界，不能溢出到场景卡片和说明区域。
- 新增关卡或素材后，逐个检查初始、动画中间帧、动画终点和失败帧的实体边界；不要只检查最终成功画面。

## 外部素材与版权

- 可以参考商业游戏的交互可读性，但不要复制任天堂、塞尔达或其他商业游戏的截图、精灵图、商标或独特美术资产。
- 外部素材优先使用 CC0 / 公共领域或项目明确允许再分发的资源；接入前确认单个素材的许可，不要只看搜索结果摘要。
- 每个外部素材都要在 `public/assets/README.md` 或等价的来源清单中记录原作者、来源链接、许可和裁剪/修改方式。
- 如果现有项目是矢量或扁平风格，优先选择能融入场景的素材，必要时通过缩放、色调或裁剪统一视觉，而不是随意拼贴风格不一致的图片。

## 本轮关卡审查结论

- 第一关：第二格必须显示拉杆；触碰后门闩应表现为向下释放的过程，而非单帧变色。
- 第二关：呼吸地板要显示实体支撑、裂纹和当前三相节奏；等待要留下脉冲反馈。
- 第三关：运行符文、远端锁孔和口袋状态都要可见；观察与应用要分别高亮对应对象。
- 第四关：记录 / 重放必须能在画面中找到实体胶囊、灯位和被唤醒的站点。
- 第五关：画出的线路必须使用玩家当前绑定；传感器触发时高亮真实线路并显示手臂动作或撞墙结果。

## 提交前检查

在 `game/` 下完成以下检查，并逐关手动确认“初始状态 → 执行动作 → 中间反馈 → 成功/失败”：

```bash
npm test
npm run build
```

如果新增或改动了关卡的 view 数据，至少为关键映射增加单测；不要只因为模拟规则没有变化就跳过表现层验证。
